# Team Chat bot, spaces, and DM dedupe

- **Bot identity**: `sender_email='companysync-bot@system'` is the ONLY key for bot styling in TeamChat.jsx. Server forces sender_email from the session on the messages endpoint, so it is unspoofable. Bot inserts go through direct SQL in `lib/chatBot.cjs` (never the HTTP endpoint).
- **Alerts space**: per-company id `conv_alerts_<companyId>`, chat_type `broadcast`, name "CompanySync Alerts", `participants='[]'`. Visible to all staff because the GET conversations query includes `chat_type='broadcast'`. Member edits on `conv_alerts_*` are rejected (400) by the members endpoint.
- **Broadcast notification fan-out**: human-sent messages to broadcast/empty-participants conversations resolve email/SMS recipients from `staff_profiles` (active, valid email, not `@system`, deduped) — NOT from the participants array. Bot posts insert directly into `chat_messages` (never via POST /api/chat/messages), so they never trigger email/SMS. Fan-out logic lives in BOTH vite-functions-plugin.js and prod-server.cjs — keep in lockstep.
- **Alerts space is created EAGERLY** on GET /api/chat/conversations (ensureAlertsSpaceEager: ON CONFLICT insert + one-time bot welcome + per-process Set cache), not just on first event. **Why**: a fresh company saw "No spaces yet" and the owner reported the feature as broken — the bot must be visible immediately.
- **Bot hook sites**: entity-API hooks (Lead create, Invoice→paid, BuildSchedule status change) plus Stripe invoice-paid paths; dev & prod each have their copies (grep `chatBot.` to enumerate). No double-post risk: Stripe paths mark paid via direct SQL (entity hooks can't also fire) and every site gates on a real transition. All calls `.catch`-isolated so bot failure never breaks the write.
- **Why records need tolerant field reads**: hook payloads are sometimes flattened, sometimes `{data:{...}}` JSONB; chatBot's `f(rec,key)` reads both. Leads have `first_name`/`last_name` columns, NOT `name` — derive display name from name || full_name || first+last or you get "Unknown" alerts.
- **DM dedupe is server-side**: POST /api/chat/conversations with type direct/dm reuses the most-recently-active existing direct conversation with the same case-insensitive participant email SET (order-independent). Client-side dmByEmail dedupe alone was insufficient (concurrent opens created dup threads and messages landed in the stale one).
- **'dm' is an API alias for 'direct'** — stored chat_type is always 'direct'.
- **File uploads from the frontend** must use `base44.integrations.Core.UploadFile({ file })` → `result.file_url`. `base44.storage` only has a stub `upload` that returns null — calling anything else there fails at runtime and only surfaces via a real browser file-picker test, not API-level tests.
- **Member validation**: adds are checked against staff_profiles + company owner + Subcontractor/Vendor emails; filter NULL `user_email` rows before `.toLowerCase()` (column is nullable → TypeError → 500).
- **Voice messages (mic)**: `message_type='audio'` must be in the allowlist in BOTH dev (vite-functions-plugin.js POST /api/chat/messages) and prod-server.cjs. Upload extension allowlists are separate too: dev is vite-integrations-plugin.js (ALLOWED_EXTENSIONS + /uploads mime map), prod is db/prod-integrations.cjs (ALLOWED + MIME_TYPES) — audio exts (.webm/.m4a/.mp3/.ogg/.wav) needed in all. Attachment messages store a URL in `message`; the server maps it to a friendly previewText ('📷 Photo'/'🎤 Voice message'/'📎 name') for last_message + email/SMS previews. Frontend: recording must be cancelled on selectedId change (else audio sends to the OLD conversation) and startRecording needs a synchronous in-flight guard (double-click before getUserMedia resolves = orphaned hot mic). E2e-testable with Chromium fake-media flags; test uploads land in public/ — delete them after.

- **Conversational Lexi is a SECOND system identity**, separate from the one-way alert bot, and the two must not be conflated: the bot broadcasts into a Space and has no reply path, Lexi only ever lives in a two-person direct thread. **Why**: a reply posted into a Space would be fanned out to the whole roster. Both identities are non-mailboxes, so the per-participant email/SMS fan-out must skip *any* `@system` address, not just the bot's — otherwise every message to Lexi bounces mail at a fake address. Her reply is inserted with direct SQL for the same reason bot alerts are.
- **Reusing an assistant inside chat needs no new tool surface.** Route the thread through the same assistant handler the assistant's own page calls, passing the *caller's own request object* so session-derived authz and per-user scoping apply unchanged. Passing a client- or message-derived email instead would let a rep act as a teammate. This avoids touching the tool registry's several parallel surfaces entirely.

**How to apply**: any new bot alert type goes in `lib/chatBot.cjs` (notifyEntityEvent) and reuses postAlert; keep dev/prod hook sites in lockstep; never post bot messages through the HTTP endpoint.
